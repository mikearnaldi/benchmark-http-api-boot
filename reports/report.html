Effect HttpApi cold start

effect npm 4.0.5 · node v24.21.0 · linux 6.18.54 · Intel(R) Xeon(R) Platinum 8370C CPU @ 2.80GHz (8 cores) · rolldown 1.2.14 · 30 fresh processes per size · Sat, 17 Oct 2026 09:13:20 GMT

Cold start is everything a brand-new process or isolate does before it can send its first response: boot the runtime, parse and compile the bundle, evaluate the modules (which in an Effect app also defines the API and builds the handler at module scope), then serve the first request with code V8 has never run before. This is what a serverless platform pays on every new instance, and what a Worker spends against its startup CPU budget. Each sample below is a fresh node process running a single rolldown bundle of an effect/http-api app with 1, 10, 50, 100, 500 endpoints.

Summary. A minimal HttpApi app cold-starts in 101 ms (27 ms Node boot, 58 ms loading the bundle, 16 ms to define, build and serve). Each endpoint adds ~153 µs, so 500 endpoints take 179 ms, and at that size the API work (90 ms) is larger than module load (61 ms). The biggest finding is that most of the post-load time is not the work itself but running it cold: rebuilding the same API in the same process once V8 has compiled and optimized the code takes 1.0 ms instead of 15.6 ms at 1 endpoint and 30 ms instead of 92 ms at 500. Cold start is therefore driven as much by how much distinct code runs at startup as by how much work it does.

1 · Anatomy of a cold start

Every phase between process start and the first response, as medians and in execution order. Module load is split into parse/compile, Effect's module evaluation and Node's undici initialization using CPU-profile shares. Define API is HttpApi.make(…).add(…) with all its schemas, and Build handler is HttpApiBuilder.group/layer + HttpRouter.toWebHandler; in a real app both run at module scope during startup. First request is one GET through the freshly built handler.

  • Small APIs are dominated by fixed cost. At 1 endpoint, 85% of the cold start happens before any API code runs. Of the 58 ms module load, ~18 ms is parsing and compiling the 552 KB bundle and ~27 ms is Node initializing undici (Node-only, see §4).

  • CPU exceeds wall time. V8's concurrent compiler and GC threads add CPU on top of the main thread: 247 ms CPU vs 179 ms wall at 500 endpoints. That matters wherever startup CPU is capped or billed.

2 · Cold code vs real work

To separate the cost of running code for the first time from the work itself, each process runs the cold pass and then rebuilds everything from scratch five more times in the same process: a new API definition, layer, handler and request each time. We report the last rebuild. The work is identical, but V8 has by then lazily compiled the functions, tiered them up from the interpreter and warmed inline caches, and any one-time lazy initialization has happened. Cold − warm is the cold-code penalty, a cost that exists only because it is a cold start.

3 · How cold start grows with API size

Cold start grows linearly: ~153 µs per endpoint on top of ~104 ms fixed (R² 0.995). Define and build share the per-endpoint cost about evenly. Module load grows only with bundle size (+0.4 KB, +6.6 µs per endpoint), and the first request is flat.

4 · Module load: the fixed part

Module load takes ~58 ms at every size, before a single line of API code runs.

  • Parse & compile (~30%) scales with bundle size. HttpApi pulls in Schema, the HTTP server stack (request/response, cookies, multipart), streams and the router whatever the API uses, so the floor is 552 KB unminified.
  • undici init (~47%, Node only). Schema.ts evaluates instanceOf(globalThis.FormData) at module scope. In Node, FormData/Request/Headers are lazy getters, and the first touch loads undici and its dependencies (30 ms even in an empty process). workerd has these natively.
  • Effect's own module evaluation (services, tags, schema singletons) is ~10 ms.

5 · Where to cut cold start

  1. Defer per-route setup to the first hit on that route. Build is 77 µs/endpoint and is paid upfront for every route. Compiling a route's codecs and handler pipeline (handlerToRoute, SchemaAST.copy/make) on first request would make cold start pay only for the routes a fresh instance actually serves.
  2. Execute less distinct code at startup. 93% (small) to 67% (large) of post-load time is cold-code penalty. Fewer generic layers on the define/build path (dual/pipe wrappers, Effect-runtime-driven layer construction for what is synchronous setup) cut both the work and the code that has to be compiled.
  3. Cheaper route registration. FindMyWay._on is the top self-time function in build. Its per-segment split/join and toLowerCase could be skipped for plain segments, or the tree could be built lazily on first lookup.
  4. Lazy FormData/File guards in Schema.ts: reading the global inside the check instead of at module scope removes ~30 ms from Node cold starts that don't otherwise need undici.
  5. For users: minify (−13 ms), enable the compile cache where the platform allows (−15 ms on Node), and reuse schema values across endpoints.

Methodology

  • Process model. Harness + generated API bundled by rolldown into one ESM file (platform: "neutral", JSDoc stripped, unminified unless stated). effect resolves from the published npm package exactly like an app. Each sample is a new node process: two discarded warmup processes per size (to warm the OS file cache only; every measured process is a cold V8 isolate), then 30 measured, run sequentially. Node's compile cache is off except in the lever experiment.
  • Cold start = time from process start (performance.timeOrigin) until the first response body has been read. Node boot is the median time-to-first-line of an empty script (27.5 ms). CPU is process.cpuUsage() at the first response (all threads).
  • API shape. G groups × E endpoints (1×1, 1×10, 5×10, 10×10, 50×10). Each group is a REST resource with an entity struct (int, strings, literal union, optional, array, nested struct), create/update payloads, a TaggedError 404, a struct 409, and list/get/create/update/delete endpoints plus actionN endpoints with their own schemas. Handlers are trivial.
  • Cold vs warm. In-process rebuilds with BENCH_WARM=5, last iteration reported, 15 processes per size.
  • Attribution. --cpu-prof at 100 µs, 5 profiles per size. Samples are assigned to phases with process.hrtime marks (the profiler's own monotonic clock) and to sources through sourcemaps chained into Effect's .ts files. Before the harness runs, samples are classified as bundle compile (under compileSourceTextModule), module code (bundle frame on the stack) or Node boot. node: frames under an undici frame count as undici init.
  • Caveats. Node is not workerd. V8 is the same, so the scaling, the cold-code penalty and the hot spots carry over, but absolute times, Node boot and the undici cost do not.
