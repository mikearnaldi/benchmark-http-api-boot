Effect HttpApi cold-start report

effect npm 4.0.5 · node v24.21.0 · linux 6.18.54 · Intel(R) Xeon(R) Platinum 8370C CPU @ 2.80GHz (8 cores) · rolldown 1.2.14 · 30 fresh processes per size · 5 CPU profiles per size · Sat, 17 Oct 2026 08:50:49 GMT

How long does an effect/http-api server take to go from a brand-new process to its first response, and how does that grow with the number of endpoints? Each sample is a fresh node process running a single rolldown bundle (the way a Cloudflare Worker ships), with APIs of 1, 10, 50, 100, 500 endpoints.

Summary. Startup is a fixed ~101 ms (27 ms Node bootstrap + 59 ms module load + ~15 ms to build and serve) plus a linear ~148 µs per endpoint, split almost evenly between defining the API (71 µs, mostly Schema construction) and building the handler (77 µs, router registration + per-endpoint codecs). At 500 endpoints, API work overtakes module load: 84 ms vs 61 ms. The first request costs a flat ~7.7 ms regardless of size because everything is built eagerly in toWebHandler.

1 · Where the time goes

Medians per phase, stacked in execution order. Module load is parse/compile + evaluation of the bundle (measured as time-to-first-harness-line minus an empty Node process). Define API is HttpApi.make(…).add(…) including all schemas. Build handler is HttpApiBuilder.group/layer + HttpRouter.toWebHandler, which builds the layer, every route and the router tree. First request is one GET /r0/1.

At 1 endpoint 85% of the time is fixed (Node + module load). At 500 endpoints the API-dependent phases are 47% of the total. Whole-process CPU is 463 ms against 180 ms wall time at 500 endpoints: V8's concurrent GC and compiler threads add CPU beyond the main thread, which matters for platforms that bill or cap all CPU.

2 · How it grows

Every API-dependent phase grows linearly with endpoint count (R² ≥ 0.991), with no super-linear term up to 500 endpoints. The cost per endpoint does fall at small sizes before settling: the first endpoints cost 398 µs each, while from 50 endpoints on it's ~143 µs. That pattern fits V8 running the definition and build code cold (interpreted, unoptimized) at first and optimizing it once it gets hot. Module load barely moves (+3.5 µs/endpoint, from parsing the generated API code), and the first request is flat.

  • Define API (71 µs/ep). Dominated by Schema (25 µs): every endpoint builds new struct/param/payload/error ASTs (schema/make.ts, SchemaAST.struct), plus HttpApi definition bookkeeping (12 µs), including validateResponseExclusivity run for every endpoint, and pipe/dual overhead (10 µs).

Next are HttpApiBuilder (13 µs: handlerToRoute, per-endpoint encoders and decoders), the Effect runtime/Layer work that runs it (7 µs), and Schema codec derivation (12 µs: SchemaAST.copy, make).

4 · Module load: the fixed cost

Module load takes ~59 ms at every size. Profiling shows Effect's own top-level code is only a small part of it:

  • Node initializing undici (~47%). Schema.ts builds instanceOf(globalThis.FormData) at module scope. In Node, FormData/Request/Headers are lazy getters, and the first touch loads undici and its dependencies (crypto, zlib, streams): 32 ms even in an empty process.
  • Parsing & compiling the bundle (~30%). Proportional to bundle size: minifying (219 KB vs 552 KB) cuts module load from 59 to 47 ms.
  • Effect's module top-level code (creating services, tags, schema singletons) is ~10 ms.

It matters elsewhere: on workerd these globals are native, so Effect's real load cost there is closer to 29 ms than 60; and a Node server using node:http (e.g. NodeHttpServer) never needs undici, so for it the reference is ~31 ms of pure waste.

5 · Bundle size

The unminified bundle starts at 552 KB and grows ~0.4 KB per endpoint, which is just the generated API code. Effect's share is the same at every size: HttpApi always pulls in Schema, the HTTP server stack (request/response, headers, cookies, multipart parsing), streams and the router, whether the API uses them or not.

6 · OpenAPI generation

OpenApi.fromApi is the most expensive per-endpoint operation measured: 158 µs/endpoint, 87 ms at 500 endpoints, with GC as its largest category (32 µs/ep). Hot spots: JSON-schema document recursion (toJsonSchemaDocument), cloneOpenAPISpec and assignProperty. It is not part of cold start: HttpApiScalar, HttpApiSwagger and openapiPath all memoize it on first request. Whoever first opens /docs on a fresh isolate pays it, though.

7 · Leads for reducing cold start

  1. Defer route compilation. Build handler cost is per endpoint and paid upfront. Compiling each route's codecs (handlerToRoute, SchemaAST.copy/make) on its first hit would make cold start pay only for the routes actually used: about 32 of the 77 µs/ep.
  2. Cheaper route registration. FindMyWay._on/on is the top self-time function in the build phase. Per-segment split("::").join(":"), split("%").join("%25") and toLowerCase could be skipped for segments without those characters, or the tree could be built lazily on first lookup.
  3. Lighter API definitions. Schema construction dominates define. Reusing schema instances across endpoints helps users; on the library side, validateResponseExclusivity and the dual/pipe layers show up per endpoint.
  4. Lazy FormData/File guards in Schema.ts (reference the global inside the check, not at module scope) save ~31 ms on Node servers that don't otherwise touch undici.
  5. Minify in deployment: about −12 ms of parse/compile for free.

Methodology

  • API shape. G groups × E endpoints (here 1×1, 1×10, 5×10, 10×10, 50×10). Each group is a REST resource: an entity struct (int, strings, literal union, optional number, array, nested struct), create/update payloads, a TaggedError 404 and a struct 409. Endpoints are list (query params), get, create, update, delete, then actionN endpoints with their own payload/success schemas, all with trivial handlers.
  • Process model. Harness + API bundled by rolldown into one ESM file (platform: "neutral", JSDoc stripped, not minified unless stated). Effect resolves from the published npm package exactly like an app. Two warmup processes per size, then 30 measured, sequentially. Node's compile cache is off.
  • Phases are timed with performance.now() inside the process. Module load = time-to-first-harness-line − median time-to-first-line of an empty script (26.5 ms).
  • Attribution. --cpu-prof at 100 µs; samples are assigned to phases with process.hrtime marks (the profiler's own clock), and to sources via sourcemaps chained into Effect's .ts files. Before the harness runs, samples are classed as bundle compile (under compileSourceTextModule), module code (bundle frame on stack) or Node bootstrap. node: frames under an undici frame count as undici init.
  • Caveats. Node is not workerd: V8 is the same, so scaling and hot spots carry over, but absolute times and the undici cost do not. The profiler inflates absolute times by ~23%, so category times are shares scaled to un-profiled medians.
